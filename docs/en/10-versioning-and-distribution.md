# 10. Versioning and distribution of the standard

## Purpose

How this standard is versioned and released, and how project repositories adopt a new version without anyone pushing changes into them directly.

## 1. Version numbers

The standard uses semantic versioning: `MAJOR.MINOR.PATCH`. The version lives in three places that must match: `package.json`, `templates/.claude/STANDARD_VERSION` and the latest heading in `CHANGELOG.md`.

| Change | Level | Examples |
| --- | --- | --- |
| Developers or repositories must act differently, or a template change can break an adopted repository | **MAJOR** | New mandatory workflow step; stricter data policy; a permission removed from `allow`; renamed placeholders; a change to the `std:` block markers in `CLAUDE.md` or to what adoption requires |
| Something new or stricter that does not break adopted repositories | **MINOR** | New rule, skill, doc or optional workflow; new deny rule; new placeholder with a safe default |
| Wording, typos, examples, clarifications with no change in meaning | **PATCH** | Fix a broken link; better Vietnamese wording |

While the major version is `0`, minor releases may contain breaking changes; they are marked **Breaking** in the CHANGELOG.

## 2. CHANGELOG discipline

- Every PR to this repository adds a line under `## [Unreleased]` in `CHANGELOG.md`, in one of: Added, Changed, Removed, Fixed, Security.
- Each line says what changed and, if needed, what adopted repositories must do (for example "replace `<unit-test-cmd>` in settings").
- Breaking changes start with **Breaking:**.
- At release time, `[Unreleased]` becomes `[x.y.z] - YYYY-MM-DD`.
- English and Vietnamese documents change in the same PR; CI checks that their structure matches.

## 3. Releasing

1. The owner of the standard opens a release PR: version bump in `package.json` and `templates/.claude/STANDARD_VERSION`, CHANGELOG heading dated.
2. CI (`standard-ci`) passes: lint, JSON, settings, parity, budget, README option tables, smoke tests.
3. After merge, the owner creates an annotated tag on `main`: `git tag -a v0.2.0 -m "Team AI standard 0.2.0"` and pushes it.
4. The owner creates a GitHub release from the tag, with the CHANGELOG section as release notes.
5. The tag starts the update job (next section).

Release cadence: after each wave retrospective during the rollout, then quarterly, and immediately for security fixes.

## 4. Three layers in a project repository

Every adopted repository has three layers. Each file belongs to exactly one layer, and each layer has one owner.

| Layer | Files | Owner | Changed by |
| --- | --- | --- | --- |
| **1. Standard** | `.claude/rules/std/**`, `.claude/agents/std-*`, `.claude/skills/std-*/**`, `.claude/std/**` (base settings, compose script, hooks, manifest), `.claude/settings.json` (generated), `.claude/STANDARD_VERSION`, `.github/pull_request_template.md` (or its `std:` block when the repository has its own template), the `team-ai-standard` block at the end of `CODEOWNERS`, the `std:` blocks in `CLAUDE.md`, `.github/workflows/std-check.yml` | Owner of the standard | Update pull requests only; never edited in the repository |
| **2. Project** | `CLAUDE.md` outside the `std:` blocks, `.claude/project.json` (stack, profile, project owner `repoOwner`, optional groups, commands, extra permission rules, hooks on/off), `.claude/rules/local/**`, the rest of `CODEOWNERS` | The repository's team | Normal pull requests |
| **3. Personal** | `.claude/settings.local.json` | Each developer | Never committed |

How the layers fit together:

- `.claude/settings.json` is generated by `.claude/std/compose-settings.mjs` from the base profile (`.claude/std/settings.<profile>.json`, Layer 1) and `.claude/project.json` (Layer 2). Command placeholders such as `<unit-test-cmd>` are replaced with the project's commands; rules for commands the project does not have are left out.
- `CLAUDE.md` has two blocks owned by the standard, generated by the same script from `.claude/project.json`: `standard` (stack, profile, which files not to edit) and `commands` (the command placeholders). Each sits between `<!-- std:begin <name> -->` and `<!-- std:end <name> -->`. Scripts change only the text inside the blocks; everything outside belongs to the repository.
- `.claude/std/manifest.json` records a hash of every Layer 1 file. The `std-check` workflow runs `compose-settings.mjs --check` on every pull request and fails when a Layer 1 file was edited, or when `settings.json` or a `std:` block is stale.
- Stack-specific statements are composable fragments: one per framework, database, data-access library and optional area (`aws`, `marketplace`). Their rules live in `.claude/rules/std/fragments/<dimension>-<value>.md` (at most 150 words each), and their examples in files with the same name next to the `std-tdd-workflow` and `std-db-migration-review` skills. The selection is recorded in `.claude/project.json` → `stack`, for example `{ "runtime": "node", "framework": "nestjs", "databases": ["mysql"], "dataAccess": "typeorm", "optional": ["aws"] }`. How to add a fragment: 11.
- `.claude/STANDARD_VERSION` holds the version the repository uses; `CLAUDE.md` refers to it instead of repeating the number.

### Personal settings (Layer 3)

Claude Code applies `.claude/settings.local.json` over the shared settings for your sessions only. From the official documentation ("Configure permissions", "Settings precedence"): "If a tool is denied at any level, no other level can allow it … if user settings allow a permission and project settings deny it, the deny rule blocks it … deny rules from any scope are evaluated before allow rules." Permission lists from different files are merged: "Claude Code combines the lists instead of picking one, so each file can add entries without removing another file's." And an `allow` rule in the local file "doesn't outrank an `ask` rule from a project or managed file". So the standard's deny and ask rules keep working when you have a local file.

| You may set in `settings.local.json` | You may not |
| --- | --- |
| Model, effort, output style and other interface preferences | Raise `cleanupPeriodDays` (keeps client code on disk longer) |
| Extra `deny` or `ask` rules (stricter for yourself) | Enable MCP servers, plugins or hooks that are not approved (doc 05) |
| Extra `allow` rules for commands the standard neither denies nor asks about (internal repositories) | Set `env` values that change the API endpoint, credentials or proxies |
| `"Yes, and don't ask again"` approvals, which Claude Code saves here | Use it to work around a rule; propose the change instead |

Claude Code adds the file to your global git excludes the first time it writes it. If you create it by hand, add `.claude/settings.local.json` to `.gitignore`.

## 5. Update pull requests

Workflow: `.github/workflows/standard-update.yml` in this repository, with `scripts/sync-standard.mjs`. Target repositories are listed in `.github/standard-targets.json`:

```json
{
  "targets": [
    { "repo": "<org>/<order-sync-service>", "baseBranch": "main" },
    { "repo": "<org>/<client-x-adapter>", "baseBranch": "develop", "enabled": false }
  ]
}
```

Stack and profile are not configured here: the job reads them from each repository's `.claude/project.json`.

When a release tag is pushed, for each enabled target the job:

1. Checks that the tag, `package.json` and `STANDARD_VERSION` agree.
2. Checks out the target repository.
3. Runs `sync-standard.mjs`, which writes **only Layer 1** (including the inside of the `std:` blocks):
   - rewrites the standard files and exactly the fragments selected in the repository's `.claude/project.json`; it deletes fragments that are no longer selected and standard files removed upstream (only files listed in its manifest);
   - updates optional groups (for example the docs checks) only if the repository installed them;
   - updates the PR template (the whole file, or only its `std:` block) and the `CODEOWNERS` block only where the managed marker or block is present;
   - replaces the text inside the `std:` blocks of `CLAUDE.md`; the text outside stays byte for byte, and a block the repository removed is reported, not added back;
   - regenerates `.claude/settings.json` from the new base profile and the repository's unchanged `.claude/project.json`;
   - writes `.claude/STANDARD_VERSION` and the manifest;
   - never changes `CLAUDE.md` outside the `std:` blocks, `.claude/project.json`, `.claude/rules/local/` or `.claude/settings.local.json`.
4. Commits to a new branch `chore/ai-standard-v<version>` and opens **one pull request** in that repository. It never pushes to the base branch.
5. The PR description lists updated and removed files, every permission rule added or removed, and anything to do by hand.

Afterwards:

- The repository's owner reviews and merges the PR like any other change. Required checks and CODEOWNERS apply.
- The job posts one announcement to the team chat with the version, the release notes link and the target repositories. Slack is the default (`SLACK_WEBHOOK_URL`); set `CHAT_PROVIDER=teams` to use Microsoft Teams (`TEAMS_WEBHOOK_URL`). Webhook URLs come only from GitHub Secrets.

Access:

The job needs write access to other repositories. **The final choice of credential is the security owner's decision.**

| Option | Setup | Why |
| --- | --- | --- |
| **Recommended: GitHub App** | Organisation-owned App installed only on the target repositories, with Contents and Pull requests write. Variable `STANDARD_APP_CLIENT_ID`, secret `STANDARD_APP_PRIVATE_KEY`. | The job creates a short-lived installation token for each target repository separately. Not tied to a person, so it survives people leaving. Every PR is shown as opened by the App. |
| Fallback: fine-grained personal access token | Token owned by a dedicated bot account, limited to the target repositories, Contents and Pull requests write, with an expiry date. Secret `STANDARD_UPDATE_TOKEN`. | Simple to set up, but long-lived, tied to an account, and must be rotated before it expires. |

The workflow uses the App when `STANDARD_APP_CLIENT_ID` is set, and the fallback token otherwise. Never use a classic personal access token or a token of a real person.

The `update` and `announce` jobs run in the GitHub environment `standard-update`. Its secrets (`STANDARD_APP_PRIVATE_KEY` or `STANDARD_UPDATE_TOKEN`, and the chat webhook) are environment secrets, never repository secrets. Configure the environment before the first release: required reviewers where the plan offers them, and deployment branches and tags limited to `v*.*.*` tags (05, sections 6 and 6.1).

- Client repositories are added to the target list only with the project lead's agreement, and are usually `enabled: false` until the client's AI position is confirmed.

## 6. Adopting the standard for the first time

Run the adoption script from the project repository (see 00-quickstart). How to read the dry run, the decision loop and a worked example: README, [Running adoption](../../README.md#running-adoption). A new project: [12](12-new-project.md).

```bash
node <path-to-standard>/scripts/adopt.mjs --profile <strict|standard> --dry-run
node <path-to-standard>/scripts/adopt.mjs --profile <strict|standard> --yes
```

Stack selection:

| Dimension | Flag | Values | Detected from |
| --- | --- | --- | --- |
| Framework | `--framework` | `nestjs`, `express`, `none` | `@nestjs/core` (wins over `express`), `express`; nothing found means `none` |
| Databases (one or more) | `--db` | `mysql`, `postgres` | `mysql2`/`mysql`, `pg`/`postgres` |
| Data access | `--data-access` | `typeorm`, `raw`, `none` | `typeorm`/`@nestjs/typeorm`; a driver without an ORM means `raw`; no database means `none` |
| Optional | `--with` / `--without-optional` | `aws` | `@aws-sdk/*`, `aws-sdk`, `aws-cdk-lib`, or an `infra/`, `cdk/` or `terraform/` folder |

- Detection is never applied silently. `--dry-run` shows the selection and where each value came from; `--yes` applies only a plan that was reviewed with `--dry-run`.
- When detection is ambiguous (for example an ORM without a database driver), or the repository depends on something the standard has no fragment for (the `unsupported` list in the registry: Fastify, Koa, hapi, Prisma, Drizzle, Kysely, Knex, Sequelize, Mongoose, MongoDB), the script stops and writes nothing. For an unsupported dependency, the message names it, says that no fragment exists, and points to 11 (add a fragment) or to the explicit flag. Framework `none` installs the fragment for a Node.js service without a web framework; data access `none` installs nothing.
- An explicit flag (or alias) overrides an unsupported dependency for that dimension. The dependency is recorded in `.claude/project.json` as `"acknowledgedUnsupported": ["@prisma/client"]`, so reviewers can see that the repository uses something without a fragment. `std-check` and update PRs warn about unsupported dependencies that are not acknowledged (for example one added later), and stay quiet about acknowledged ones.
- Invalid combinations are rejected: a data-access library without a database, a database with data access `none`, or an unknown value. Unusual ones (two databases, NestJS with a raw driver) give a warning.
- Aliases from earlier versions still work and set every dimension: `--stack nestjs-mysql` (NestJS + MySQL + TypeORM + AWS), `--stack nestjs-postgres` (NestJS + PostgreSQL + TypeORM + AWS), `--stack node-postgres` (no framework + PostgreSQL + TypeORM + AWS).
- The values and detection rules live in `templates/fragments/fragments.json`. It lists only the fragments the team uses; new ones are added through 11.

Review, then apply:

- `--dry-run` writes nothing in the repository. It prints every file to create, a unified diff of every file to change, the `.claude/project.json` it will write, the permission rules carried over or dropped with the reason, optional cleanup suggestions, the decisions required, and a **plan hash** computed from the standard version, the flags, the existing files and the result. The hash is recorded outside the repository (a per-user temporary folder).
- `--yes` recomputes the plan. If the hash differs from the reviewed one (a file edited in between, another flag, a new standard version), it stops and asks for a new `--dry-run`. `--plan <hash>` requires a specific plan instead of the recorded one.
- Before it changes any existing file, `--yes` requires a git repository with a clean working tree, on a branch other than the default branch; otherwise it stops and prints the exact git commands. Creating new files has no such condition.
- Running `--yes` again, or `--dry-run` after it, reports "Nothing to do".
- A later run fills commands that are still `null` in `.claude/project.json` from `package.json` scripts (for example after scaffolding an empty repository, doc 12) and lists them under "Commands filled from package.json". Commands already set are never replaced.
- Configuration choices (stack, profile, `--repo-owner`, `--with-docs`) are stored in `.claude/project.json`. On a later run each value comes from a flag, then `project.json`, then detection, then the default, and `--dry-run` prints the source of each. A later run with a flag changes only that value: `project.json` keeps its other keys, the settings and `std:` blocks are regenerated, and standard files the new selection no longer needs are removed. It requires the repository to be on the same version of the standard (update first). Update pull requests read the same values, including `repoOwner` for the `CODEOWNERS` block. Every option: README, "Adoption options" (generated from `scripts/lib/adopt-options.mjs`; `adopt.mjs --help` prints the same list).

What is automatic:

- New files: the Layer 1 files, `.claude/project.json` (selection, commands pre-filled from `package.json` scripts where the names match, extra permission rules), a `CLAUDE.md` skeleton with `TODO(adopt)` sections when there is none, `.claude/STANDARD_VERSION` and the manifest. A new `CODEOWNERS` gets the project owner from `--repo-owner`.
- An existing `CLAUDE.md` gets the two `std:` blocks after its first H1 and introduction (before the next heading; at the start when there is no H1). Every existing line is kept. Headings that may repeat a block (such as "Commands") are reported as optional cleanup and never removed.
- An existing `.claude/settings.json` is regenerated from the profile. Its `deny` and `ask` rules that the profile does not have are moved into `.claude/project.json` → `permissions`. An `ask` rule that a profile `deny` covers is dropped and reported. Each `allow` rule is classified in the dry run under "Existing allow rules": **covered** when a profile `allow` already matches it, including the bare form (`Bash(pnpm test)` is covered by `Bash(pnpm test *)`), so nothing is decided; **unsafe — cannot be carried** when it could match any command a profile `ask` or `deny` matches (for example `Bash(pnpm migration:run)` under the ask `Bash(pnpm migration:run *)`, or a broad `Bash(pnpm *)`), so it is dropped and adoption refuses to carry it even when asked. A rule that runs a package script (`npm run <name>`, `pnpm <name>`, `yarn <name>` and their `run` forms) is resolved first: adoption reads `package.json`, follows every script it calls (including npm `pre`/`post` scripts and `run-s`/`run-p`/`npm-run-all`), and when any command in the chain is asked or denied by the profile, the rule is **unsafe** and the dry run shows the chain, for example `pnpm verify → pnpm check → cdk synth (profile asks Bash(cdk *))`. Otherwise the rule **needs decision**, always with a hint: read-only, runs a long-lived process, uses cloud credentials, runs repository code, runs a package script (with the commands it reaches), edits files, or "no known category: check what it runs". Values the profile owns, such as `cleanupPeriodDays`, take the profile value and are listed.
- An existing PR template or `CODEOWNERS` gets the standard block at the end; the rest is kept. The block gives `CLAUDE.md` and the guard files (05, section 4) to `repoOwner`; without `--repo-owner`, the dry run suggests setting it.
- A re-run on a repository that had `common/marketplace-integration.md` (before 0.8.0) keeps the `marketplace` fragment and records it in `stack.optional`, with the source shown in the dry run, unless `--with` or `--without-optional` decides otherwise.

What stops for a decision (listed under "Decisions required" with the flag; `--yes` refuses until resolved):

- No `CODEOWNERS` and no `--repo-owner`.
- Each `allow` rule that needs a decision, one by one: `--carry-allow "<rule>"` keeps it in `.claude/project.json` → `permissions.allow`, `--drop-allow "<rule>"` drops it, and `--drop-allow-rest` drops every rule not named. Repeat the flags for several rules. The flags apply to the first adoption only; later, edit `.claude/project.json`. Permissions are never loosened automatically.
- Ambiguous stack detection or a dependency without a fragment (see above).
- A settings file that cannot be parsed or has keys the standard does not merge (`env`, `hooks`, `model`, `permissions.defaultMode` and others), or a standard file path that already exists with other content. Fix the file, or pass `--propose-unresolved`: only then does adoption write `<file>.proposed` and `.claude/std-adoption-checklist.md` for these files. The `std-check` workflow fails if a `*.proposed` file, the checklist or `.claude/settings.local.json` is committed.

Also:

- It refuses to run while the standard's own `CODEOWNERS` block still has placeholder owners.
- The checkout of the standard it runs from must be a release: a clean working tree, HEAD on the tag `v<version>` of its `package.json`, and `package.json` equal to `templates/.claude/STANDARD_VERSION`. `--dry-run` prints `Standard checkout: <tag>` and, when it is not a release, a warning with the git commands that fix it; `--yes` refuses. `--allow-unreleased` (maintainers testing unreleased changes) lifts the refusal and is printed in both outputs. `sync-standard.mjs` run by hand applies the same check, and its summary records the override; in GitHub Actions the update job checks the tag against the version instead.
- It never commits, pushes, installs packages or uses the network.
- To undo before committing: `git restore .` and `git clean -fd` (check first with `git clean -nd`).
- Afterwards the owner of the standard adds the repository to `standard-targets.json`.

## 7. Skipping or delaying an update

- A repository owner may delay an update PR (for example during a release freeze), but not longer than the next minor release.
- Security releases are merged within 5 working days.
- If a repository cannot adopt a change, the owner records the exception with the owner of the standard (reason, end date).
